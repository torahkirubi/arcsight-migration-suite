## 1. Project Goal
We are building a SOC (Security Operations Center) detection-engineering tool from scratch. Its purpose is to migrate legacy ArcSight ESM correlation rules to modern SIEM platforms (Microsoft Defender XDR (KQL) and Splunk (SPL)). For data-sensitivity reasons, this tool will rely exclusively on a local LLM (Qwen2.5 Coder, served via LM Studio) instead of cloud APIs.

There will be two pipelines:
*   **Direct path (ArcSight → KQL/SPL):** The primary focus. It skips intermediate layers and translates the rule directly.
*   **Legacy path (ArcSight → Sigma → KQL/SPL):** Translates into Sigma YAML first, validates via pySigma, then converts to KQL/SPL. 

## 2. Core Architectural Principle
The driving insight: **Anything that can be extracted deterministically from the source rule MUST be extracted via code, rather than asked of the LLM.** 
A local model is great at translating boolean logic, but unreliable at strict syntax and lacks real-world knowledge (like current product coverage). The system routes each sub-task to the right engine: regex parsing, the LLM, pySigma, or a human.

## 3. Backend Requirements (FastAPI)
You will need to build the following modular backend services:

*   **Deterministic Extraction (`arcsight_parser.py`):** Use regex (zero LLM involvement) to extract the Rule Name, Priority-to-Severity mapping, Frequency, Group-by fields, and the MITRE ATT&CK tactic (pulled directly from ArcSight's `eventAnnotationStage` URI). *Known pitfall to avoid:* ArcSight exports often drop closing parentheses per clause. Use `And`/`Or` keyword boundaries for extraction rather than paren-balancing.
*   **LLM Translation (`llm_client.py`):** Wrap LM Studio's `/v1/chat/completions` endpoint (configurable via an `LM_STUDIO_BASE_URL` env var, usually pointing to `host.docker.internal:1234/v1`). The LLM will receive the raw boolean condition logic (`Contains/EQ/And/Or`) and a field-mapping cheat sheet.
*   **Coverage Validation (`translation_validator.py`):** Deterministically extract required and excluded match-terms from the ArcSight condition text. Validate that the generated KQL/SPL contains all required terms, and that all exclusion terms are present *in a negated context* (to prevent false positives).
*   **Runbook Generation (`threat_analysis.py`):** Use the LLM to generate threat analysis, missing triage fields, and Tier-1 analyst triage guides. *Strict Safety Boundary:* The LLM must NEVER generate Microsoft Defender (MDE) coverage assessments. MDE coverage must be engineered as a strictly human-entered field.
*   **Live Splunk Validation (`splunk_client.py`):** A read-only client that runs the translated SPL as a bounded `oneshot` search against a real Splunk instance REST API to fetch real hit counts and syntax errors.
*   **Audit Logging:** Implement a lightweight persistent store (e.g., SQLite mounted as a Docker volume) to log every translation, validation, and test-firing with timestamps and pass/fail states.

## 4. Frontend Requirements (React + Tailwind)
Build a modular frontend (e.g., React via Vite, React Query for state/polling) that interfaces with the FastAPI backend. It must feature:

*   **Data-Driven UI:** Render data according to its trustworthiness. For example, the `mitre_source` field must visually distinguish whether the MITRE tactic was actually extracted from the rule or was missing. The MDE coverage assessment must be a distinct, human-input form field.
*   **Background Health Check:** Poll backend endpoints every 30-60s to check the reachability of the FastAPI server, LM Studio, and the Splunk instance. Display these as a persistent status indicator (colored badges) in the header.
*   **Audit Log View:** A dedicated tab or modal to view the SQLite history of all translation runs.
*   **Git-Ready Output:** The UI must support merging the LLM runbook, human MDE inputs, and translated queries into a downloadable `.txt` file ready for a Git commit.
